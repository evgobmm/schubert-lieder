# Рабочий процесс

Обновлено: 2026-08-14. Источник — указания пользователя (чат).

## Запись указаний (главное правило процесса)

1. **Каждое указание пользователя из чата фиксируется в `docs/rules/`** — в том же ходе работы, не «потом». Указания не должны жить только в чате.
2. Правила — **не истина последней инстанции**: они могут меняться.
3. Если новое указание **противоречит записанному** — правило переписывается (при неясности — спросить пользователя), и **пользователю всегда явно сообщается в чате, что переписано** (было → стало). В самих файлах правил историю изменений не хранить: правила содержат только текущую редакцию, без пометок «переписано с...» — иначе они раздуваются.
4. **Без пометок «указание пользователя, дата» у отдельных правил** — дату даёт строка «Обновлено» в шапке файла, источник по умолчанию — указания пользователя. Правило формулируется как правило, а не как протокол его получения.
5. Технический страж: хук в `.claude/settings.json` напоминает об этом при каждом сообщении пользователя.
6. Реестр правил — `docs/rules/index.md`; при добавлении файла правил обновлять реестр.

## Структура репозитория

- Корень — только: `CLAUDE.md`, `README.md`, `docs/`, `planning/`, `app/`, служебные (`.github/`, `.claude/`, `.gitignore`).

Перед волной оценивать остаток пула (≈0,4M токенов Fable на песню) и резать состав волны под него; недоделанные песни ждут в scratchpad, догоняются отдельным прогоном только этапов Fable + сверка.

Проценты /usage переводить в токены именно так — через ccusage за дни текущего окна, а не через «субтокены» воркфлоу.
- **Возобновление воркфлоу (`resumeFromRunId`) кэширует только НЕПРЕРЫВНЫЙ ПРЕФИКС вызовов `agent()`, а не «все завершённые агенты».** Перепись 2026-08-24 по замеру волны №4 (было: «завершённые агенты возвращаются из кэша БЕСПЛАТНО, если (prompt, opts) не изменились» — стало: бесплатен только префикс до ПЕРВОГО изменившегося ИЛИ УПАВШЕГО вызова; всё, что в порядке вызовов идёт после него, выполняется живьём заново, даже если в прошлом круге оно успешно завершилось). Замер: круг 2 волны №4 стоил **78,8M и продвинул волну на 2 песни** — словарные агенты (самое начало цепочек) вернулись из кэша побайтно, а факты, страницы, Fable и сверки пересчитались заново с другими результатами (у D 805: факты 34→39, аннотации 14→15). Причина — падения в круге 1 (обрыв связи на словаре D 553/D 524 в первые минуты): всё после них стало «живым». **Следствие — правило продолжения после обрыва: если в оборвавшемся круге были падения не в самом конце, `resumeFromRunId` НЕ применять** — это почти полный повторный прогон по цене нового. Вместо него собрать остаток скриптом `wave-remaining.js` и запустить НОВЫЙ воркфлоу только по остатку (полная цепочка / только Fable / только ремонт — скрипт печатает готовые args для каждого случая). Resume остаётся уместен ровно в одном случае: круг оборвался чисто по лимиту, без падений в середине. Прочее по-прежнему в силе: перед resume не менять ни скрипт, ни промпты, ни пути каталога; тяжёлый запуск не начинать в конце 5-часового окна.
- **Волна из 50 песен в одно 5-часовое окно сессии не помещается** (замер 2026-08-24): круг идёт ~3,1 ч и упирается в лимит сессии примерно на 22 песнях из 50. - **Устойчивость к падению воркспейса и исчерпанию лимитов: ничего критичного не должно жить только в scratchpad/tmp.** Скрипты конвейера, партии, карта и результаты — коммитятся в репозиторий и пушатся **сразу** по получении: результат каждой партии публикуется и уходит в git до запуска следующей. **Контейнерный лимит параллельности (обязателен): не более 2 тяжёлых воркфлоу одновременно.** Память WSL2 пока не увеличиваем (решение пользователя); если её поднимут до 10–12 ГБ — лимит можно вернуть к 3. Контейнер имеет 7,6 ГБ RAM; три воркфлоу по ~14 агентов уже валили VS Code пользователя (прецеденты: сессия транскрипции и 2026-08-17, load 32/16 ядер, 223 МБ свободной памяти, ugrep агента съел 3 ГБ). **Урок 2026-08-17: поллинг-сторож недостаточен** — ugrep раздувается до гигабайт за секунды, и reload window у пользователя случались НЕСМОТРЯ на сторожа с интервалом 30–45 с (полагаться на «монитор предотвратит» нельзя). Оборона в два эшелона: (1) **сторож-киллер**: интервал 5 с, убийство ugrep уже с ~4% RAM, тихий режим (события — в /tmp/claude-1000/memory-guard.log). **С 2026-08-18 сторож автоматизирован: скрипт `planning/scripts/memory-guard.sh` (идемпотентный, lock-файл) автозапускается SessionStart-хуком в `.claude/settings.json`** — потому что «записанная, но запускаемая вручную» защита не сработала: в ночной прогон 2026-08-18 сторож запущен не был, контейнер набрал 17 oom_kill, и у пользователя дважды падал воркспейс (reload window). Полагаться на ручной запуск запрещено; (2) **предпочтительно — ограничитель на бинарь**: обернуть вендоренный ugrep в `ulimit -v` (~700 МБ), чтобы разогнавшийся поиск умирал сам за миллисекунды (путь бинаря ловить через `/proc/<pid>/exe` живого процесса; обёртка не переживает переустановку CLI — команду фиксировать здесь же). Главный индикатор — память, не load. Дисковая фиксация промежуточных результатов (досье, журналы) обязательна всегда.
