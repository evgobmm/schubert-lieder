# Рабочий процесс

Обновлено: 2026-08-14. Источник — указания пользователя (чат).

## Запись указаний (главное правило процесса)

1. **Каждое указание пользователя из чата фиксируется в `docs/rules/`** — в том же ходе работы, не «потом». Указания не должны жить только в чате.
2. Правила — **не истина последней инстанции**: они могут меняться.
3. Если новое указание **противоречит записанному** — правило переписывается (при неясности — спросить пользователя), и **пользователю всегда явно сообщается в чате, что переписано** (было → стало). В самих файлах правил историю изменений не хранить: правила содержат только текущую редакцию, без пометок «переписано с...» — иначе они раздуваются.
4. **Без пометок «указание пользователя, дата» у отдельных правил** — дату даёт строка «Обновлено» в шапке файла, источник по умолчанию — указания пользователя. Правило формулируется как правило, а не как протокол его получения.
5. Технический страж: хук в `.claude/settings.json` напоминает об этом при каждом сообщении пользователя.
6. Реестр правил — `docs/rules/index.md`; при добавлении файла правил обновлять реестр.

## Структура репозитория

- Корень — только: `CLAUDE.md`, `README.md`, `docs/`, `planning/`, `app/`, служебные (`.github/`, `.claude/`, `.gitignore`).
- **Приложение целиком в `app/`** (package.json, vite, src, public) — файлы приложения не смешиваются с правилами и планированием.

## Устойчивость и гигиена сессий

- **После обрыва/перезагрузки сессии** — не доверять памяти разговора: проверять фактическое состояние по диску, git и журналам воркфлоу; докладывать, что реально сделано, что потеряно.
- **Смена подписки — `/login` на лету**: пользователь переключается между двумя Pro-подписками командой `/login` прямо посреди сессии; сессия, контекст и работающие воркфлоу переживают смену без остановки (проверено 2026-08-17, дважды). Паузить волны для переключения не нужно. Нюанс: запросы, летевшие в момент смены, могут оборваться («Connection lost») — упавшие агенты добираются через `resumeFromRunId` из кэша, это штатно.
- Фоновые исследования оформлять воркфлоу (журнал на диске → возобновление из кэша после обрыва).
- **Экономия лимитов: расходовать токены бережно, без потери качества.** Практически: (1) **модель указывается ЯВНО в каждом вызове агента** — без явного `model` субагент наследует модель главного цикла (Fable, самый дорогой и самый тесный пул; урок 2026-08-18: ночные волны без `model` исчерпали Fable-лимит аккаунта до 100%, план «дешёвая модель для механики» не был воплощён в коде запуска). Лестница: `haiku` — механика; `sonnet` — сбор цитат/фактов/словарные дорожки, извлечение из источников; `opus` — русские тексты (перевод, аннотации, «О песне»), приёмка, арбитраж; **Fable — главный цикл сессии, точечный арбитраж и ОБЯЗАТЕЛЬНЫЙ финальный редакторский проход по каждой песне перед публикацией** (указание пользователя 2026-08-18: когда Fable выпал из всех этапов, материал страниц стал ощутимо отличаться от эталона «Гретхен»; черновую массу пишут sonnet/opus, но последнее слово по языку, тону и отбору — за Fable). Пул Fable отдельный от «All models» и заметно меньше — проход экономный (правки, не переписывание; ~100–150k на песню), бюджетировать по /usage; **калибровка окон (замер 2026-08-18, /usage пользователя)**: недельное окно «All models» одного аккаунта ≈ 65–70 млн субтокенов (15 п.п. = ~10 млн sonnet/opus); песня полного конвейера сейчас ≈ 1,3–1,5 млн ≈ 2 п.п. окна, целевая после калибровки ≈ 1 п.п.; главный цикл (Fable) за ночь оркестровки съедает ~4 п.п. своего пула — бюджетировать и его; каждую волну планировать в процентах окна и сверять с /usage пользователя; (2) **сначала бесплатные источники данных** (OCR-слой MDZ, готовые файлы, curl+скрипты) — зрение по картинкам только как fallback для спорных мест; (3) проверки делать скриптами (мультимножества слов, диффы), а не агентами, где возможно; (4) большие данные не гонять через контекст основной сессии; (5) оплаченные результаты упавших воркфлоу вытаскивать из журналов, не запуская работу заново; (6) **агентам в промпте явно запрещать спавнить собственных субагентов** — исследовательские хвосты выполняет один последовательный дешёвый агент, веер только через Workflow под контролем; (7) в конце 5-часового окна тяжёлые запуски не начинать; (8) **автономная работа без пользователя (ночь): не жечь лимиты бессмысленно, но и не экономить в ущерб качеству** — скриптовые/сетевые шаги в приоритете (почти бесплатны); тяжёлые шаги делать, когда они нужны для качества результата, — эффективно, дешёвой моделью где возможно, малыми партиями с коммитом после каждой; к возвращению пользователя работа должна быть доведена и выверена. Параллельность агентов не ограничиваем по контейнеру, но объём «в полёте» держим малым (см. ниже).
- Результаты исследований сразу сохранять в `planning/research/` и коммитить.
- Разовую ошибку сборки не диагностировать по одному прогону: сначала повторить (возможна гонка с параллельной сессией, пишущей файлы). Сборку для сайта делает CI; локальная — только проверка.
- JSON-данные песен править через jq (адресация по структуре) либо после свежего чтения файла; крупные замены — сборкой нового объекта с валидацией (`jq -e`) до записи.
- При обрыве воркфлоу (перезагрузка, лимит) — возобновлять через `resumeFromRunId`: завершённые агенты возвращаются из кэша журнала.
- **Устойчивость к падению воркспейса и исчерпанию лимитов: ничего критичного не должно жить только в scratchpad/tmp.** Скрипты конвейера, партии, карта и результаты — коммитятся в репозиторий и пушатся **сразу** по получении: результат каждой партии публикуется и уходит в git до запуска следующей. **Контейнерный лимит параллельности (обязателен): не более 2 тяжёлых воркфлоу одновременно.** Память WSL2 пока не увеличиваем (решение пользователя); если её поднимут до 10–12 ГБ — лимит можно вернуть к 3. Контейнер имеет 7,6 ГБ RAM; три воркфлоу по ~14 агентов уже валили VS Code пользователя (прецеденты: сессия транскрипции и 2026-08-17, load 32/16 ядер, 223 МБ свободной памяти, ugrep агента съел 3 ГБ). **Урок 2026-08-17: поллинг-сторож недостаточен** — ugrep раздувается до гигабайт за секунды, и reload window у пользователя случались НЕСМОТРЯ на сторожа с интервалом 30–45 с (полагаться на «монитор предотвратит» нельзя). Оборона в два эшелона: (1) **сторож-киллер**: интервал 5 с, убийство ugrep уже с ~4% RAM, тихий режим (события — в /tmp/claude-1000/memory-guard.log). **С 2026-08-18 сторож автоматизирован: скрипт `planning/scripts/memory-guard.sh` (идемпотентный, lock-файл) автозапускается SessionStart-хуком в `.claude/settings.json`** — потому что «записанная, но запускаемая вручную» защита не сработала: в ночной прогон 2026-08-18 сторож запущен не был, контейнер набрал 17 oom_kill, и у пользователя дважды падал воркспейс (reload window). Полагаться на ручной запуск запрещено; (2) **предпочтительно — ограничитель на бинарь**: обернуть вендоренный ugrep в `ulimit -v` (~700 МБ), чтобы разогнавшийся поиск умирал сам за миллисекунды (путь бинаря ловить через `/proc/<pid>/exe` живого процесса; обёртка не переживает переустановку CLI — команду фиксировать здесь же). Главный индикатор — память, не load. Дисковая фиксация промежуточных результатов (досье, журналы) обязательна всегда. Текущее состояние конвейера — `planning/catalog/transcription-state.md` (обновлять после каждой партии): по нему новая сессия продолжает с места обрыва.
