# Рабочий процесс

Обновлено: 2026-08-14. Источник — указания пользователя (чат).

## Запись указаний (главное правило процесса)

1. **Каждое указание пользователя из чата фиксируется в `docs/rules/`** — в том же ходе работы, не «потом». Указания не должны жить только в чате.
2. Правила — **не истина последней инстанции**: они могут меняться.
3. Если новое указание **противоречит записанному** — правило переписывается (при неясности — спросить пользователя), и **пользователю всегда явно сообщается в чате, что переписано** (было → стало). В самих файлах правил историю изменений не хранить: правила содержат только текущую редакцию, без пометок «переписано с...» — иначе они раздуваются.
4. **Без пометок «указание пользователя, дата» у отдельных правил** — дату даёт строка «Обновлено» в шапке файла, источник по умолчанию — указания пользователя. Правило формулируется как правило, а не как протокол его получения.
5. Технический страж: хук в `.claude/settings.json` напоминает об этом при каждом сообщении пользователя.
6. Реестр правил — `docs/rules/index.md`; при добавлении файла правил обновлять реестр.

## Структура репозитория

- Корень — только: `CLAUDE.md`, `README.md`, `docs/`, `planning/`, `app/`, служебные (`.github/`, `.claude/`, `.gitignore`).

## Устойчивость и гигиена сессий

- **После обрыва/перезагрузки сессии** — не доверять памяти разговора: проверять фактическое состояние по диску, git и журналам воркфлоу; докладывать, что реально сделано, что потеряно.
- Фоновые исследования оформлять воркфлоу (журнал на диске → возобновление из кэша после обрыва).
- **Экономия лимитов: расходовать токены бережно, без потери качества.** Практически: (1) механическим задачам (транскрипция, извлечение, сверка) — **дешёвая модель (`model:'haiku'` или `'sonnet'`) и `effort:'low'`**; дорогая модель — для арбитража/проверки смысла; **однократные критичные исследования, результаты которых переиспользуются многократно (дайджесты, реестры, справочники), — на самой сильной доступной модели: на них не экономить**; (2) **сначала бесплатные источники данных** (OCR-слой MDZ, готовые файлы, curl+скрипты) — зрение по картинкам только как fallback для спорных мест; (3) проверки делать скриптами (мультимножества слов, диффы), а не агентами, где возможно; (4) большие данные не гонять через контекст основной сессии; (5) оплаченные результаты упавших воркфлоу вытаскивать из журналов, не запуская работу заново; (6) **агентам в промпте явно запрещать спавнить собственных субагентов** — исследовательские хвосты выполняет один последовательный дешёвый агент, веер только через Workflow под контролем; (7) в конце 5-часового окна тяжёлые запуски не начинать; (8) **автономная работа без пользователя (ночь): не жечь лимиты бессмысленно, но и не экономить в ущерб качеству** — скриптовые/сетевые шаги в приоритете (почти бесплатны); тяжёлые шаги делать, когда они нужны для качества результата, — эффективно, дешёвой моделью где возможно, малыми партиями с коммитом после каждой; к возвращению пользователя работа должна быть доведена и выверена. Параллельность агентов не ограничиваем по контейнеру, но объём «в полёте» держим малым (см. ниже).
- Результаты исследований сразу сохранять в `planning/research/` и коммитить.
- Разовую ошибку сборки не диагностировать по одному прогону: сначала повторить (возможна гонка с параллельной сессией, пишущей файлы). Сборку для сайта делает CI; локальная — только проверка.
- JSON-данные песен править через jq (адресация по структуре) либо после свежего чтения файла; крупные замены — сборкой нового объекта с валидацией (`jq -e`) до записи.
- При обрыве воркфлоу (перезагрузка, лимит) — возобновлять через `resumeFromRunId`: завершённые агенты возвращаются из кэша журнала.
- **Устойчивость к падению воркспейса и исчерпанию лимитов: ничего критичного не должно жить только в scratchpad/tmp.** Скрипты конвейера, партии, карта и результаты — коммитятся в репозиторий и пушатся **сразу** по получении: результат каждой партии публикуется и уходит в git до запуска следующей. **Контейнерный лимит параллельности (обязателен): не более 2 тяжёлых воркфлоу одновременно.** Память WSL2 пока не увеличиваем (решение пользователя); если её поднимут до 10–12 ГБ — лимит можно вернуть к 3. Контейнер имеет 7,6 ГБ RAM; три воркфлоу по ~14 агентов уже валили VS Code пользователя (прецеденты: сессия транскрипции и 2026-08-17, load 32/16 ядер, 223 МБ свободной памяти, ugrep агента съел 3 ГБ). При работающих волнах держать постоянный Monitor нагрузки (load average и available RAM из `free`); при load > ~24 или available < ~500 МБ — убивать разогнавшиеся поисковые процессы (ugrep и т.п.) и приостанавливать последний запущенный воркфлоу (возобновление — `resumeFromRunId`, оплаченное вернётся из кэша). Дисковая фиксация промежуточных результатов (досье, журналы) обязательна всегда. Текущее состояние конвейера — `planning/catalog/transcription-state.md` (обновлять после каждой партии): по нему новая сессия продолжает с места обрыва.
