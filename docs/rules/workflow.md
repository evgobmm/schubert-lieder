# Рабочий процесс

Обновлено: 2026-08-14. Источник — указания пользователя (чат).

## Запись указаний (главное правило процесса)

1. **Каждое указание пользователя из чата фиксируется в `docs/rules/`** — в том же ходе работы, не «потом». Указания не должны жить только в чате.
2. Правила — **не истина последней инстанции**: они могут меняться.
3. Если новое указание **противоречит записанному** — правило переписывается (при неясности — спросить пользователя), и **пользователю всегда явно сообщается в чате, что переписано** (было → стало). В самих файлах правил историю изменений не хранить: правила содержат только текущую редакцию, без пометок «переписано с...» — иначе они раздуваются.
4. **Без пометок «указание пользователя, дата» у отдельных правил** — дату даёт строка «Обновлено» в шапке файла, источник по умолчанию — указания пользователя. Правило формулируется как правило, а не как протокол его получения.
5. Технический страж: хук в `.claude/settings.json` напоминает об этом при каждом сообщении пользователя.
6. Реестр правил — `docs/rules/index.md`; при добавлении файла правил обновлять реестр.

## Структура репозитория

- Корень — только: `CLAUDE.md`, `README.md`, `docs/`, `planning/`, `app/`, служебные (`.github/`, `.claude/`, `.gitignore`).
- **Приложение целиком в `app/`** (package.json, vite, src, public) — файлы приложения не смешиваются с правилами и планированием.
- `docs/rules/` — правила; `planning/` — исследования и справочные материалы.
- **Агенты и скрипты не пишут временные файлы в репозиторий** — только в scratchpad-директорию сессии. В промпт каждого агента включать это требование. Обнаруженный мусор — удалять.

## Устойчивость и гигиена сессий

- **После обрыва/перезагрузки сессии** — не доверять памяти разговора: проверять фактическое состояние по диску, git и журналам воркфлоу; докладывать, что реально сделано, что потеряно.
- Фоновые исследования оформлять воркфлоу (журнал на диске → возобновление из кэша после обрыва).
- **Качество и скорость важнее экономии**: параллельных агентов искусственно не ограничиваем — основная нагрузка агентов ложится на серверы модели, а не на контейнер. За нагрузкой контейнера периодически следить (`free`, `uptime`) и реагировать только при реальных признаках проблем.
- Результаты исследований сразу сохранять в `planning/research/` и коммитить.
- Разовую ошибку сборки не диагностировать по одному прогону: сначала повторить (возможна гонка с параллельной сессией, пишущей файлы). Сборку для сайта делает CI; локальная — только проверка.
- JSON-данные песен править через jq (адресация по структуре) либо после свежего чтения файла; крупные замены — сборкой нового объекта с валидацией (`jq -e`) до записи.
- При обрыве воркфлоу (перезагрузка, лимит) — возобновлять через `resumeFromRunId`: завершённые агенты возвращаются из кэша журнала.
- **Устойчивость к падению воркспейса и исчерпанию лимитов (указание пользователя): ничего критичного не должно жить только в scratchpad/tmp.** Скрипты конвейера, партии, карта и результаты — коммитятся в репозиторий и пушатся **сразу** по получении: результат каждой партии публикуется и уходит в git до запуска следующей. Одновременно — не больше 1–2 тяжёлых воркфлоу (чтобы обрыв по лимиту не потерял большой незафиксированный объём). Текущее состояние конвейера — `planning/catalog/transcription-state.md` (обновлять после каждой партии): по нему новая сессия продолжает с места обрыва.
